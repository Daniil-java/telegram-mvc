# План разработки telegram-mvc

Цель: библиотека для Spring Boot, в которой Telegram-бот описывается контроллерами с аннотациями,
а хендлеры возвращают `View` вместо прямых вызовов Telegram API. Сначала библиотека и примеры
в этом репозитории, потом перенос нескольких ботов manageapp.

Оценки даны в вечерах (≈2–3 часа). Каждый этап заканчивается тем, что можно запустить
или проверить тестом, а не только кодом «на будущее».

## Принципы

- **Библиотека не знает про приложение.** Никаких сущностей, БД и enum'ов конкретного проекта.
  Всё, что зависит от приложения (пользователи, хранилище, отчёты об ошибках, права), делается
  через интерфейсы с разумной реализацией по умолчанию.
- **Ошибки разработчика ловятся при старте.** Конфликт маршрутов, неизвестный параметр метода,
  неверный тип возврата: приложение не запускается и пишет понятную причину.
- **Хендлер не трогает Telegram API.** Только `View` на выходе. Это даёт тесты без сети.
- **telegrambots изолирован.** Классы библиотеки telegrambots используются только в транспорте
  и рендерере, чтобы обновление её версии затрагивало два пакета.
- **Без лишнего.** Webhook, i18n, групповые чаты и inline-режим добавляются только при реальной
  потребности.

## Структура пакетов (целевая)

```
com.kuklin.telegrammvc
├── annotation      @BotController, @CommandHandler, @ActionHandler, @InputHandler, …
├── autoconfigure   TelegramMvcAutoConfiguration, TelegramMvcProperties
├── transport       регистрация ботов, long polling, BotClient
├── context         BotContext, UpdateType, ChatUser
├── routing         HandlerRegistry, RouteKey, RoutePattern, UpdateDispatcher
├── invoke          MethodInvoker, ArgumentResolver и встроенные резолверы
├── view            View, Keyboard, Button, RenderStrategy, CallbackData
├── render          ViewRenderer, правила фоллбэков, ответы на callback
├── error           BotUserException, ExceptionResolver, ErrorReporter
├── interceptor     BotInterceptor, InterceptorChain, встроенные интерцепторы
├── state           AwaitInput, InputStateStore, ShortIdStore
└── send            BotSender, BotResponder
```

Модуль `telegram-mvc-test` (этап 7) — тестовый набор для пользователей библиотеки.

## Этап 1. Транспорт и конфигурация

Цель: бот из конфигурации подключается к Telegram и получает апдейты. Обработки ещё нет, только лог.

- [ ] **T1.1 `TelegramMvcProperties`.** `telegram-mvc.bots.<name>.token`, `.username`, `.enabled` (по умолчанию `true`). Валидация: пустой токен у включённого бота — ошибка старта с именем бота.
- [ ] **T1.2 `BotClient`.** Обёртка над `AbsSender` одного бота: `execute(BotApiMethod)` и отправка медиа. Единственное место, где вызывается `execute`.
- [ ] **T1.3 Регистрация ботов.** Для каждого включённого бота создаётся long-polling бот и регистрируется в `TelegramBotsApi`. Апдейты передаются в интерфейс `UpdateConsumer(String botName, Update)`.
- [ ] **T1.4 Корректная остановка.** При остановке контекста сессии polling закрываются, без висящих потоков.
- [ ] **T1.5 Пул обработки.** Апдейты обрабатываются в пуле потоков (`telegram-mvc.executor.threads`, по умолчанию 4), а не в потоке polling. Порядок апдейтов одного чата сохраняется (очередь на чат или striped-executor).
- [ ] **T1.6 Тесты.** Свойства и валидация через `ApplicationContextRunner`; бот с `enabled: false` не регистрируется.
- [ ] **T1.7 Пример.** `simple-bot` пишет в лог тип каждого апдейта.

**Готово, когда:** `simple-bot` с реальным токеном логирует присланные сообщения и нажатия.

## Этап 2. Маршрутизация MVP

Цель: сценарии 1 и 2 из проектного документа: команда → новое сообщение, кнопка → редактирование.

- [ ] **T2.1 Аннотации.** `@CommandHandler(value, description, hidden)`, `@ActionHandler(value)`. `@BotController(bot)` уже есть.
- [ ] **T2.2 `BotContext`.** Неизменяемый объект: имя бота, `UpdateType` (COMMAND, ACTION, TEXT, MEDIA, OTHER), chatId, `ChatUser` (id, username, имя, язык), messageId, routeKey, args, исходный `Update`.
- [ ] **T2.3 `UpdateContextFactory`.** Update → BotContext. Команда: отрезать `@botname`, отделить аргументы. Callback: data как routeKey.
- [ ] **T2.4 `HandlerRegistry`.** Сканирует бины с `@BotController` после инициализации контекста (`SmartInitializingSingleton`). Таблица `bot → (тип, ключ) → HandlerMethod`. Дубликат ключа в одном боте — ошибка старта с указанием обоих методов. Контроллер для бота, которого нет в конфигурации, — тоже ошибка.
- [ ] **T2.5 `MethodInvoker`.** Вызов через `MethodHandle`, подготовленный при старте. На этом этапе поддерживаются параметры `BotContext` и отсутствие параметров.
- [ ] **T2.6 `View` (минимум).** `View.text(...)` → builder: `row()`, `button(text, data)`, `urlButton`, `strategy(...)`, `build()`. Неизменяемый.
- [ ] **T2.7 `ViewRenderer` (минимум).** `NEW` → `SendMessage`, `EDIT` → `EditMessageText`. `AUTO`: команда → NEW, кнопка → EDIT. На каждый callback ровно один `answerCallbackQuery`.
- [ ] **T2.8 `UpdateDispatcher`.** Собирает цепочку: контекст → поиск хендлера → вызов → рендер. Не нашёл хендлер — лог и пустой ответ на callback.
- [ ] **T2.9 Тесты.** Реестр (поиск, дубликаты), фабрика контекста (разбор команд с `@botname` и аргументами), рендерер с подменённым `BotClient`.
- [ ] **T2.10 Пример.** `simple-bot`: меню `/start` с двумя кнопками и «Назад» — пример из README становится рабочим.

**Готово, когда:** пример из README работает в Telegram без изменений кода.

## Этап 3. Аргументы и шаблоны

Цель: хендлеры получают нужные данные параметрами, кнопки несут переменные.

- [ ] **T3.1 SPI `ArgumentResolver`.** `supports(MethodParameter)`, `resolve(BotContext, MethodParameter)`. Пользовательские резолверы подхватываются как бины.
- [ ] **T3.2 Встроенные резолверы.** `BotContext`, `Update`, `ChatUser`, `@ChatId long`, `@MessageId Integer`, `@Args String`, `@Text String`.
- [ ] **T3.3 Шаблоны кнопок.** `RoutePattern`: сегменты через `:`, переменные `{name}`, хвост `*`. Приоритет: точное совпадение → больше литеральных сегментов → переменные → `*`.
- [ ] **T3.4 Индекс шаблонов.** Мапа по первому сегменту, внутри — отсортированный список. Конфликт двух шаблонов с одинаковой формой — ошибка старта.
- [ ] **T3.5 `@Param`.** Значение переменной шаблона с конвертацией через Spring `ConversionService`: `long`, `int`, `String`, `UUID`, `enum`, `LocalDate`. Ошибка конвертации — `BotUserException("Кнопка устарела")`.
- [ ] **T3.6 `CallbackData`.** `CallbackData.of("usr", "del", id)`. Проверка 64 байт в UTF-8 и запрет `:` внутри сегмента. `View.button(text, CallbackData)` наравне со строкой. Превышение — исключение в `build()`.
- [ ] **T3.7 Проверки сигнатур при старте.** Параметр без резолвера, `@Param` без переменной в шаблоне, неподдерживаемый тип возврата — ошибка старта с именем метода.
- [ ] **T3.8 Тесты.** Таблица «шаблон × data → совпадение/переменные», конвертация, все проверки старта.
- [ ] **T3.9 Пример.** Список элементов с кнопками `item:show:{id}` и пагинацией `item:page:{n}`.

**Готово, когда:** пагинация в примере работает, а намеренно сломанный контроллер не даёт запустить приложение.

## Этап 4. Полная отрисовка

Цель: ответы Telegram обрабатываются ядром, хендлеру о них думать не нужно.

- [ ] **T4.1 Стратегии.** `REPLACE` (удалить + отправить), `DELETE`, `NONE`. EDIT без исходного сообщения → NEW.
- [ ] **T4.2 Ответы на кнопку.** `toast(text)` и `alert(text)` в `View`. Возможен View только с toast (`NONE`).
- [ ] **T4.3 Форматирование.** `parseMode` (HTML по умолчанию), утилита `Html.escape()`, `disablePreview`, `silent`.
- [ ] **T4.4 Медиа.** Фото и документ: `byte[]`, `File`, URL, `file_id`. EDIT над медиа-сообщением → `editMessageCaption` / `editMessageMedia`. Смена типа текст ↔ медиа → REPLACE.
- [ ] **T4.5 Клавиатуры.** Reply-клавиатура, `removeKeyboard()`.
- [ ] **T4.6 Типы возврата.** `View`, `List<View>`, `String` (короткая запись), `void`/`null`.
- [ ] **T4.7 Таблица фоллбэков.** `message is not modified` → игнор; `message can't be edited` / `not found` → NEW; `can't parse entities` → повтор без разметки + warn; 429 → ожидание `retry_after` и один повтор; 403 → событие `BotBlockedEvent` (приложение само решает, что делать).
- [ ] **T4.8 Длинный текст.** Больше 4096 символов (подпись — 1024): для NEW разбить по абзацам, для EDIT — исключение.
- [ ] **T4.9 Тесты.** На каждую строку таблицы фоллбэков: подменённый `BotClient` бросает нужную ошибку, проверяем следующий вызов.

**Готово, когда:** все строки таблицы покрыты тестами.

## Этап 5. Ошибки и интерцепторы

Цель: понятное поведение при сбоях и общий код до и после хендлеров.

- [ ] **T5.1 `BotUserException`.** Сообщение показывается пользователю: alert на кнопке, NEW в остальных случаях.
- [ ] **T5.2 `@BotExceptionHandler`.** Метод контроллера, параметры: исключение, `BotContext`, остальные резолверы. Возвращает `View`.
- [ ] **T5.3 `@BotControllerAdvice`.** Глобальные обработчики, можно ограничить ботом.
- [ ] **T5.4 Обработчик по умолчанию.** Текст «Что-то пошло не так» (настраивается в properties), лог error.
- [ ] **T5.5 SPI `ErrorReporter`.** Вызывается для неожиданных ошибок с контекстом (бот, чат, маршрут, исключение). По умолчанию только лог. Ошибка внутри обработчика ошибок — только лог, без рекурсии.
- [ ] **T5.6 `BotInterceptor`.** `before(ctx) → Optional<View>` (прервать), `after(ctx, view, error)`. Порядок через `@Order`. Привязка к боту или ко всем.
- [ ] **T5.7 Встроенные интерцепторы.** `LoggingInterceptor` (одна строка: бот, чат, маршрут, мс, результат), `DoubleClickGuard` (повторный callback, пока идёт обработка → toast «Секунду…»).
- [ ] **T5.8 Доступ.** Аннотация `@RequiresAccess("admin")` + SPI `AccessPolicy`. Отказ → настраиваемый View.
- [ ] **T5.9 Тесты.** Порядок поиска обработчиков, прерывание цепочки, двойной клик в двух потоках.

**Готово, когда:** исключение в примере показывает пользователю текст и вызывает `ErrorReporter`.

## Этап 6. Ввод и медиа

Цель: сценарии 3–5: ввод данных, свободный текст и фото, долгие операции.

- [ ] **T6.1 `AwaitInput`.** `View.awaitInput(key)` и `awaitInput(key, data)`. Запись: бот, chatId, key, data, expiresAt.
- [ ] **T6.2 SPI `InputStateStore`.** Реализация по умолчанию в памяти с TTL (`telegram-mvc.input.ttl`, 15 минут). Приложение может подменить на БД.
- [ ] **T6.3 `@InputHandler(key)`.** Параметр `@InputData String` для data из ожидания. Ожидание снимается после успешного вызова. Если хендлер снова вернул `awaitInput` — продлевается.
- [ ] **T6.4 Порядок маршрутизации.** Callback → команда (сбрасывает ожидание) → ожидание ввода → медиа → текст → fallback. Тесты на каждый переход.
- [ ] **T6.5 Обработчики сообщений.** `@TextHandler`, `@PhotoHandler`, `@VoiceHandler`, `@DocumentHandler`, `@FallbackHandler`. Не больше одного каждого типа на бота. Резолверы `PhotoSize` (наибольшее), `Voice`, `Document`.
- [ ] **T6.6 Несовпадение типа ввода.** Ждали текст, пришло фото → ответ «Жду текст», ожидание сохраняется.
- [ ] **T6.7 Fallback по умолчанию.** Неизвестная команда или устаревшая кнопка → короткий ответ со ссылкой на `/help`.
- [ ] **T6.8 `BotResponder`.** Параметр хендлера: `typing()`, `progress(View)` — отправить промежуточное сообщение, которое финальный View отредактирует.
- [ ] **T6.9 Пример `notes-bot`.** Заметки: добавление через ввод, список с удалением, фото как вложение. Хранение в памяти.

**Готово, когда:** в `notes-bot` можно добавить, посмотреть и удалить заметку, а команда посреди ввода корректно его отменяет.

## Этап 7. Вне хендлеров и тесты

Цель: отправка из планировщиков, автоматическое меню команд, удобные тесты для пользователей.

- [ ] **T7.1 `BotSender`.** `send(bot, chatId, View)` для кода вне хендлеров. Те же правила отрисовки.
- [ ] **T7.2 Рассылки.** `sendAll(bot, chatIds, View)` с ограничением скорости (≈25 сообщений/с) и обработкой 429/403.
- [ ] **T7.3 Меню команд.** При старте `setMyCommands` по `description` из `@CommandHandler` (кроме `hidden`). Выключается свойством.
- [ ] **T7.4 Автоматический `/help`.** Если у бота нет своего хендлера `/help`, ответить списком команд.
- [ ] **T7.5 `ShortIdStore`.** Длинные данные для кнопки: `CallbackData.stored(...)` кладёт данные в хранилище и возвращает короткий ключ. Протухший ключ → fallback «Меню устарело».
- [ ] **T7.6 Модуль `telegram-mvc-test`.** Fluent API: `botTest("notes").command("/start").expectText(...).press("note:add").expectAwaitInput("note:text").send("текст").expectText(...)`. Без сети, с записью всех вызовов `BotClient`.
- [ ] **T7.7 Перевести тесты примеров** на `telegram-mvc-test`.

**Готово, когда:** сценарий `notes-bot` целиком покрыт тестом из T7.6.
